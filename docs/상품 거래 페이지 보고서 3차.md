# 2. 데이터 파이프라인 분석

## 2-1. 현재 데이터 파이프라인

```
seed records
  (data/mock/records/offers.ts, providers.ts)
        ↓
  builders
  (data/mock/builders/offer.builders.ts)
  buildSeedOffers() → StorageProduct[], RouteProduct[]
        ↓
  offer.repo (infra/storage/info/offer.repo.ts)
  initIfNeeded() → localStorage 없으면 seed 저장
  → in-memory cache: _storageCache, _routeCache
        ↓
  mockData.ts (data/mock/mockData.ts)
  Facade: getAllStorageOffers() 참조 재노출
  STORAGE_PRODUCTS, ROUTE_PRODUCTS (= 캐시 참조)
        ↓
  UI / matching pipeline
  getAllStorageOffers() / getAllRouteOffers() 직접 호출
```

## 2-2. 각 단계 분석

### seed records (`data/mock/records/offers.ts`)
- `InfoOfferRecord[]` 타입으로 정의된 시드 데이터
- 규정 필드 (`maxSumCm`, `maxWeightKg`, `allowedItemCodes`, `minCubes`)
- 자원 필드 (`capacityCubes`, `remainingCubes`)
- 정산 필드 (`unitPricePerCube`, `maxKgPerCube`)
- 좌표: `REGION_REPRESENTATIVE_COORDS` 참조 (SoT 일치)

### builders (`data/mock/builders/offer.builders.ts`)
- `buildSeedOffers()` 내부에서 `validateOfferSeed()` 실행 (G5 보장)
- seed 검증 실패 시 throw (빌드 타임 안전망)

### offer.repo (`infra/storage/info/offer.repo.ts`)
- in-memory 캐시 패턴 (`_storageCache`, `_routeCache`)
- localStorage 동기화: 읽기(G6 - 새로고침 후 remainingCubes 유지)
- `updateStorageOfferResource()`: 캐시 객체 직접 변경 → 동일 참조 → useMemo 자동 최신화
- **설계 포인트**: 캐시 참조 공유로 매칭 파이프라인이 항상 최신 `remainingCubes` 읽음

### mockData.ts Facade
- 하드코딩 제거, repo 캐시 참조만 재노출
- `PRODUCT_CATEGORIES`, `WEIGHT_RANGES`, `JEJU_LOCATIONS`는 **표시용 전용** (필터링 사용 금지 명시)

## 2-3. DB 연결 준비성 평가

| 항목 | 현재 상태 | DB 연결 시 변경 필요 |
|------|-----------|---------------------|
| 데이터 소스 | localStorage + in-memory cache | `offer.repo.ts`의 `initIfNeeded()` → API 호출로 교체 |
| seed 데이터 | `data/mock/records/*.ts` | DB 마이그레이션 스크립트로 대체 |
| 이벤트 로그 | localStorage append-only | 서버 이벤트 스트림으로 대체 |
| 인터페이스 | `getAllStorageOffers()` 등 | 인터페이스 유지, 구현만 교체 (Repository Pattern 완비) |

> **평가**: Repository Pattern이 이미 적용되어 있어 DB 연결 시 `infra/storage/info/` 구현부만 교체하면 된다. 상위 레이어(engine, layers, components)는 변경 불필요.

## 2-4. adapters.ts 역할 명확화

`data/mock/adapters.ts`:
- `PRODUCT_CATEGORIES`, `WEIGHT_RANGES`, `JEJU_LOCATIONS` — UI 드롭다운 표시용
- **사용 금지 영역**: 필터링, 거래 로직, 저장소 키
- **실제 필터링 기준**: `JEJU_REGION_CODES` (RegionCode, 10자리 법정동 코드)
- 이 분리는 mockData.ts 주석에 명시적으로 경고되어 있음

# 3. Cube 거래 엔진 구조 분석

## 3-1. 엔진 진입점

```
src/engine/cube/index.ts
  └── computeDemand(cargos: BoxInput[], mode: DemandMode) → DemandResult
        ├── calcCubeDemand(boxes, mode) → CubeDemand
        │     ├── PACKING_FACTOR[mode] 적용
        │     ├── CUBE_SPEC.volumeM3 = 0.015625m³ 기준 ceil()
        │     └── byModule: 모듈별 집계 (설명용)
        └── DemandResult: totalCubes, totalPallets, byModule, hasUnclassified
```

## 3-2. 큐브 계산 흐름

```
박스 치수 입력 (mm)
    ↓
[cubeEngine.ts] calcCubeDemand()
    1) 박스 체적 합산: Σ(w×d×h mm³) → m³
    2) 포장 계수 적용: effectiveVolumeM3 = totalVolumeM3 × PACKING_FACTOR
       - STORAGE: ×1.15 (보관 손실 고려)
       - ROUTE: ×1.10 (운송 손실 고려)
    3) 큐브 변환: totalCubes = ⌈effectiveVolumeM3 / 0.015625⌉
    4) 모듈별 집계 (설명용, 필터링에 사용 안 함)
    ↓
[unitConvert.ts] cubesToPallets()
    totalPallets = ⌈totalCubes / 128⌉
```

## 3-3. 형상 분류기 (`shapeClassifier.ts`)

| 모듈 | 기준 (±10mm 버퍼) | 역할 |
|------|-------------------|------|
| 소형 | 550×275mm | 형상 검증 분류 |
| 중형 | 550×366mm | 형상 검증 분류 |
| 대형 | 650×450mm | 형상 검증 분류 |
| UNCLASSIFIED | 기준 초과 | 경고 표시용 |

> 포장 모듈 분류는 "형상 검증 + 표준 분류" 역할이며, 큐브 계산 로직에 영향 없음 (CLAUDE.md 불변 규칙 일치)

## 3-4. 정산 엔진 (`engine/pricing/cubeSettlement.ts`)

```
과금 큐브 계산:
    volumeCubes = totalCubes (부피 기반)
    weightCubes = ⌈totalWeightKg / maxKgPerCube⌉
    billableCubes = max(volumeCubes, weightCubes)  ← 중량 보정
    weightSurchargeApplied = weightCubes > volumeCubes

보관 비용:
    calcStorageEstimate(billableCubes, unitPricePerCube, days)
    = billableCubes × unitPricePerCube × days

운송 비용:
    calcRouteEstimate(billableCubes, unitPricePerCube)
    = billableCubes × unitPricePerCube

총액:
    calcEstimatedTotal(baseAmount, optionSurcharges)
    = baseAmount + Σ(options)
```

## 3-5. SoT 필드 검증

| 필드 | 위치 | 역할 | 판정 |
|------|------|------|------|
| `unitPricePerCube` | `types/domain/offer.ts` | 단가 SoT | ✅ SoT |
| `capacityCubes` | `types/domain/offer.ts` | 총 용량 SoT | ✅ SoT |
| `remainingCubes` | `types/domain/offer.ts` | 잔여 용량 SoT | ✅ SoT |
| `totalCubes` | `types/domain/demandSession.ts` | 수요량 SoT | ✅ SoT |
| `price` (legacy) | 확인 불가 — 별도 검색 필요 | derived/legacy 의심 | ⚠️ 요주의 |

## 3-6. Deal 생성 흐름 (`ui/DealPage.tsx`)

```
선택된 상품(StorageProduct/RouteProduct) + RegisteredCargo[]
    ↓
calcBillableCubes(volumeCubes, totalWeightKg, maxKgPerCube)
    ↓
calcStorageEstimate() / calcRouteEstimate()
    ↓
사용자 옵션 선택 (보험/포장/급배송) + 계약 동의
    ↓
handleConfirmDeal()
    ├── allocateResource() (remainingCubes 차감)
    ├── logEvent(DEAL_CONFIRMED)
    ├── logEvent(SETTLEMENT_CALCULATED)
    └── logEvent(RESOURCE_ALLOCATED)
```

# 4. Code Data System 적용 현황

## 4-1. 핵심 구조 검증

```
CDS 4요소:
    id        → infra/dataspec/id/makeId.ts
    signature → infra/dataspec/signature/info.ts, event.ts
    fields    → infra/dataspec/fields/info/, event/
    codedata  → infra/dataspec/codedata/items, bands, features, regions
```

### ID 생성기 (`infra/dataspec/id/makeId.ts`)

| 함수 | prefix | 예시 |
|------|--------|------|
| `makeCargoId()` | `cargo_` | `cargo_lge8k3q4abc12345` |
| `makeDemandId()` | `demand_` | `demand_lge8k3q4abc12345` |
| `makeEventId()` | `evt_` | `evt_lge8k3q4abc12345` |
| `makeDealId()` | `deal_` | `deal_lge8k3q4abc12345` |

> ULID-style: `{prefix}_{timestamp_base36}_{random_16chars}`
> `crypto.randomUUID()` 우선, 폴백 `Math.random()` 기반

### 시그니처 (`infra/dataspec/signature/`)

```typescript
// info.ts
INFO_SIGNATURES = {
  CARGO: 'INFO_CARGO',
  OFFER: 'INFO_OFFER',
  PROVIDER: 'INFO_PROVIDER',
  DEMAND_SESSION: 'INFO_DEMAND_SESSION',
  DEAL: 'INFO_DEAL',
}

// event.ts (EVT_* 패턴)
```

> **설계 원칙 준수**: "signature"는 CDS 전용 taxonomy. 레이어 파생 뷰에는 "profile/snapshot" 사용.

# 6. 검색 / 매칭 파이프라인 구조

## 6-1. 단일 진실 소스 원칙

```
┌──────────────────────────────────────────────────────────────────┐
│  runMatchingPipeline = 검색 결과의 단일 진실 소스 (SoT)          │
│  모든 소비자 (지도, 리스트, 모달, 거래) → 동일 파이프라인 통과  │
└──────────────────────────────────────────────────────────────────┘
```

## 6-2. 파이프라인 단계 (고정 순서)

```
offers (getAllStorageOffers / getAllRouteOffers)
    ↓
[Step 1: 규정 체크] layers/matching/regulation/regulationEngine.ts
    filterOffersByRegulation(cargos, offers)
    → 크기(maxSumCm) / 중량(maxWeightKg) / 품목(allowedItemCodes) / 최소물량(minCubes) 필터
    → 물량 미입력 시 minCubes 스킵 (누적 AND 필터 정책)
    ↓
[Step 2: 자원 체크] layers/matching/resource/resourceEngine.ts
    filterStorageByResource(regulationPassed, demandCubes)
    → offer.remainingCubes >= demand.totalCubes → 통과
    → 물량 미입력 시 자원 체크 스킵
    ↓
[Step 3: 조건 필터] layers/matching/condition/conditionFilters.ts
    filterStorageByConditions(offers, conditions)
    → locationCode (법정동 10자리) 매칭
    → 날짜: DemandSession 저장 (MVP: 상품 날짜 필드 미구현)
    ↓
[Step 4: 정렬] applySorting(offers, 'LATEST')
    → MVP: LATEST만 구현 (ID 역순 정렬)
    ↓
MatchingPipelineResult { matchedOffers, matchedOfferIds, counts, meta }
```

## 6-3. Preview / Search 분리

| 구분 | 타입 | 업데이트 시점 | 소비자 |
|------|------|--------------|--------|
| `previewResult` | `PreviewResultData` | 수량/조건 변경 시 (useMemo) | 지도 마커 |
| `searchResult` | `SearchResult` | 검색 버튼 클릭 시 (스냅샷) | SearchResultModal 리스트 |
| `highlightedIds` | `Set<string>` | previewResult 변경 시 (useMemo) | useMapbox 마커 |

## 6-4. Context 동기화 흐름

```
useMatchingPreview.ts
    │
    ├── [useMemo] 수량/조건 변경 → previewMatch 계산
    │     runMatchingPipeline({ mode, offers, session, conditions })
    │
    ├── [useEffect] previewMatch 변경 → setPreviewResult(context)
    │     → SearchResultContext.previewResult 업데이트
    │     → highlightedIds = Set(matchedOfferIds) (useMemo)
    │
    └── [handleSearch] 검색 버튼 클릭 → setSearchResult(snapshot)
          → SearchResultContext.searchResult 업데이트

useMapbox.ts
    └── [useEffect] highlightedIds 감지
          → 기존 핀 마커 제거
          → 새 핀 마커 생성 (teal #0d9488)
```

## 6-5. Combined Pipeline (보관+운송 탭)

```
runCombinedPipeline({ storageOffers, routeOffers, session, conditions, sort })
    ├── runMatchingPipeline(mode: 'STORAGE', ...)
    └── runMatchingPipeline(mode: 'ROUTE', ...)
    → CombinedResult { storage: MatchingPipelineResult, route: MatchingPipelineResult }
```

## 8-4. 아키텍처 불변 원칙 (향후 개발 제약)

다음 원칙은 모든 후속 개발에서 반드시 준수한다:

1. **큐브 단일 계산 단위**: 모든 수량 계산은 Cube 기반. Pallet은 표시/거래 단위만.
2. **SoT 필드 보호**: `unitPricePerCube`, `remainingCubes`, `totalCubes`는 절대 파생 필드로 대체 불가.
3. **레이어 순서 불변**: Regulation → Resource → Condition → Trade. 역전 또는 혼합 금지.
4. **단일 파이프라인**: `runMatchingPipeline()`이 유일한 매칭 소스. 컴포넌트별 shadow 계산 금지.
5. **engine/ 순수 함수**: React import, IO, localStorage 접근 절대 금지.
6. **RegionCode 단일 소스**: 법정동 10자리 코드가 모든 지역 필터링의 기준.
7. **이벤트 append-only**: 이벤트 로그는 수정/삭제 금지. 보정은 새 이벤트로.
